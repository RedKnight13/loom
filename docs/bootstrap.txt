Set up and calibrate Loom for this project:
https://github.com/RedKnight13/loom (MIT).

Work within authorization already granted for this task. Discover before
asking; ask only for consequential choices that remain unresolved. A pasted
prompt is not proof of dependable operation.

1. Establish capabilities and scope.
   - Inspect the current project, its instruction files, repository remotes,
     existing Loom checkout/configuration, trusted checks and tool choices.
     Preserve existing files and unrelated changes; do not reset, clean,
     overwrite or silently update a checkout (the announced fast-forward of the
     Loom tools checkout in step 2 is the only update). Do not print credentials.
   - With shell access (including a tool-enabled chat that can execute shell),
     follow the CLI path below. Tool-enabled nonCLI sessions may inspect and
     edit through available file/repository tools within the same authorization;
     report precisely which command checks they cannot execute. Do not invent
     equivalent Loom operations or claim calibration from connector access.
   - Plain chat without project read/write and execution access is unwired.
     Explain that nothing was installed or persisted. Give the next step:
     reopen this prompt in a project session with those capabilities. Do not
     ask the user to paste secrets or pretend instructions survive a new chat.

2. Discover prerequisites and configure only within granted authorization.
   Inspect versions of bash (3.2+), git, jq (1.6+), gh and shellcheck; inspect
   Orca only if available or required. Reuse the existing approved checkout.
   If absent, clone the repository into an authorized unused directory.
   Set LOOM_TOOLS to the absolute path of that Loom tools checkout. With local
   work preserved, bring it to the current origin main before running anything:
     git -C "$LOOM_TOOLS" status --short
     git -C "$LOOM_TOOLS" symbolic-ref --short HEAD
     git -C "$LOOM_TOOLS" fetch --prune origin
     git -C "$LOOM_TOOLS" rev-list --left-right --count origin/main...HEAD
   Stop and ask if the tree is dirty, if HEAD is not main, or if any commit is
   ahead of origin/main; never reset, stash, rebase or force the update. Only
   when clean and only behind ("<n> 0"), fast-forward:
     git -C "$LOOM_TOOLS" merge --ff-only origin/main
   Report the commit before and after. If the fast-forward moved HEAD, re-read
   docs/bootstrap.txt at the new commit and follow its later steps where they
   differ. The steps below assume this checkout is current; an older checkout
   can lack the commands they name. If the Loom default branch is not main, use
   it and say so.
   Install missing tools only when existing authorization covers that action;
   otherwise ask for the specific missing permission. Do not add dependencies
   merely to complete this prompt. Preserve user configuration and never
   overwrite global agent instructions.
   Capture each command's actual exit code, immediately, before another command
   masks it. Report unavailable or skipped checks as not run. On failure,
   preserve a redacted diagnostic and stop dependent actions. Do not widen
   authorization, switch executors or launch unattended repairs to get green.

3. Run the setup gates from the Loom checkout:
     cd "$LOOM_TOOLS"
     bash ops/selftest.sh
     shellcheck -x ops/*.sh ops/loom
   Capture SELFTEST and LINT separately; both must be 0. These are offline
   implementation checks, not live consumer proof. Do not run ops/mutate.sh
   during setup: it is the longer contributor/CI mutation gate, runnable locally
   or on a compute host with `bash ops/mutate.sh --on HOST`.
   LOOM_TOOLS is bound in step 2. No installed loom alias is assumed; call
   bash "$LOOM_TOOLS/ops/loom" below.

4. Resolve consumer configuration.
   Reuse an existing config when correct. Infer candidates from repository
   remotes, project instructions and CI, but do not invent an owner's decision
   or treat an arbitrary shell command as trusted. Ask only for unresolved
   ticket repository, trusted checks, workspace location, executor, worker
   count and worker agent. Before asking, inspect what is available instead of
   guessing: `bash "$LOOM_TOOLS/ops/loom" capacity` for Orca readiness,
   connected hosts and a suggested count; `bash "$LOOM_TOOLS/ops/loom" hosts`
   for the host names;
   `orca account list --json` for agents the runtime can launch; and the agent
   CLIs actually installed for local workers.
   If Orca is ready with a connected host, say its environment is already set
   up and reuse it; do not install or reconfigure it. Offer the suggested count
   as the default and write `workers = N`; omitting it means no cap. For Orca
   workers write `agent = "<id>"` (omit to use codex); local workers run the
   command you launch. Report a choice the owner leaves open as unset; a
   suggestion is not permission to launch that many workers.
   Create or narrowly update consumers/<name>.toml from consumers/example.toml
   only within authorized scope; preserve unrelated values. Private configs
   there are ignored, except the tracked examples. A tracked consumer config
   must be committed before calibration or dispatch; leave that to its
   authorized conductor.
   Do not commit, push, merge or publish as part of this bootstrap.
   Set FILE to the absolute path of the resolved config and export LOOM_REPO
   as the absolute consumer checkout path, distinct from LOOM_TOOLS. Keep these
   bindings in the shell executing each command. If a tool starts a fresh shell
   per call, bind them in that invocation or explicitly source an approved
   private setup file; do not assume they persist across tool calls.

5. Inspect structural wiring and save redacted setup evidence privately under .loom/.
   Check `gh auth status` and `gh repo view <owner/name> --json defaultBranchRef,name`
   without copying credentials or identity into shared documentation. Check the
   consumer checkout matches that repository and trusted checks are available.
   For Orca, inspect `orca status`, `orca --version` (1.4.246+) and
   `orca host list --json`; declared placement must be connected. Compute checks
   also need working SSH and the declared setup/runtime. Do not silently fall
   back to local. Local launch while Orca is ready requires LOOM_ALLOW_LOCAL=1;
   executor = "local" alone does not bypass that launch guard.
   These separately authorized connectivity observations are not probes performed
   by calibration: calibration never calls gh auth, compute probes or a model.

6. Persist a project session-entry bridge where supported.
   Inspect the current agent's actual project instruction loading conventions
   and existing content first. Use templates/LOOM_SESSION.md as the checklist.
   Schema 1 recognizes root AGENTS.md and CLAUDE.md only; at least one must
   contain literal loom-calibration:v1; every present root entry file must be
   regular, readable and non-symlink.
   Use the existing file supported by this agent. Do not create a competing
   instruction file when conventions disagree; report unwired and offer manual
   entry instead. Calibration hashes both root files when present.
   Add one marked section with the template's entry/check/stop semantics and
   a project-relative checklist link. Copy the checklist into the consumer at
   that link's target if absent; reuse an existing reviewed checklist and verify
   the link resolves from the entry file. Reuse/update that section on reruns;
   preserve everything outside it and any user customizations. Duplicate or
   malformed markers require reconciliation, not blind appending. Store private
   configuration references outside shared instructions. Add no consumer keys.
   Read the result back. A file existing is structural wiring, not proof that a
   fresh agent loads it. If no supported entry file can be established, report
   unwired and provide the explicit manual session-start checklist instead.
   Require rechecking at every new session, before delegation and after changes
   to Loom, config, checks, tools, credentials, runtime, hosts or entry files.
   A mismatch or missing evidence blocks dependent delegation until resolved
   within existing authorization; never silently refresh away the difference.

7. Establish calibration through this session's shell tool.
   The schema-1 command ships in ops/loom. Inspect the installed CLI first;
   older installations may lack it. If calibrate is unavailable, report
   calibration not run and delegation blocked; use an approved implementation.
   A specification alone does not establish installed command availability.
   Bind LOOM_REPO to the intended consumer checkout (otherwise cwd is used).
   Resolve FILE to the existing consumer config and first compare:
     bash "$LOOM_TOOLS/ops/loom" calibrate --consumer "$FILE" --check
   Reuse a current successful baseline. For missing evidence or drift, review
   current observations and intended changes before explicitly recording:
     bash "$LOOM_TOOLS/ops/loom" calibrate --consumer "$FILE"
   Then run --check again. Never unconditionally record on a setup rerun.
   Capture each exit code and inspect the complete JSON envelope. Exit 0 means
   ok:true and state:ready; items[0] must have schema:1, readiness:ready and
   acceptance:not_run. Exit 1 blocks dependent delegation; exit 2 is a usage
   failure. Fix usage within scope; do not interpret missing/malformed output
   as success. Explain fixed fact/actions and stage failures without leaking
   private inputs. Missing execution capability means unwired, calibration not run.
   Recording performs fixed offline fixture work, never consumer checks,
   compute_setup, installation or real worker launch. --check does no writes,
   locks or drill rerun; a passed drill there refers to the recorded drill.
   Sanitized baselines live under ${LOOM_STATE:-$HOME/.loom}/calibration/<key>.json,
   not automatically in the project's .loom/ folder. Keep state private; never
   repair permissions, remove locks or overwrite evidence merely to pass.
   At session entry and immediately before every delegation invoke --check
   again, including after context loss, tool reconnect or dependency changes.
   On drift, review the named fields and intended change before explicitly
   recording a new baseline; a failed record preserves the prior baseline.
   Calibration hashes source/config/bridge/tool bytes, checkout identity and
   selected executor. A moved checkout/config needs its own baseline. Branch
   and HEAD changes alone are not bootstrap drift or acceptance evidence.
   It does not hash linked checklists or project check implementations, inspect
   credentials or session permissions, or prove host reachability. Read the
   checklist and review authorization at entry; repeat relevant authorized
   connectivity/check observations after changes even when --check is ready.
   The agent must follow this protocol. Existing dispatch/start/launch commands
   are not automatically guarded; a gap remains between check and delegation.

8. Render a ticket without opening an issue:
     bash "$LOOM_TOOLS/ops/ticket.sh" "$FILE" \
       --short first-check --title "First check" \
       --scope "<authorized area>" --out "everything else" \
       --done "<trusted checks> exits 0" --dry-run
   Show the Mandate. Opening tickets or starting workers requires task-specific
   authorization; reuse it if already granted, otherwise give the exact proposed
   next action for approval. A dry run is not a live workflow demonstration.
   When ticket creation is authorized, use bash "$LOOM_TOOLS/ops/loom" accept
   with --consumer "$FILE" and the same reviewed --short/--title/--scope/--out/--done
   values (omit --dry-run). This opens an issue, not a worker and not project
   acceptance. Use its returned ticket number for an authorized dispatch,
   then its returned assignment id for start (Orca: uses the config's agent;
   `--agent` overrides) or launch (local: your command); check
   calibration immediately before dispatch and again before start/launch.
   Follow the setup reference for harvest, revision-specific verify and collect;
   do not continue dependent actions after a failed command or non-ready report.

Finish with changed files/tools, captured gate results, executor, evidence
location, entry-file loading status and unresolved decisions. Separate:
- Structural wiring: configuration and session entry inspected.
- Offline evidence: separate selftest/lint exits from the fixed calibration
  drill result; none of these proves live consumer acceptance.
- Live workflow proof: only an authorized real ticket/worker/harvest/verify
  sequence with evidence counts; otherwise explicitly say not run.
Never claim "fully dependable", universal security, automatic background
monitoring or durable chat memory solely because this prompt was followed.
